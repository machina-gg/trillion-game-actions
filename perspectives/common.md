# 共通観点（全 PR）

すべてのリポジトリ・すべての PR に適用する観点と、判定・投稿の規約。
プロファイル別の観点（`harness.md` / `chrome-extension.md` 等）は、このファイルに**足す**形で適用する。

⚠ **ここに書かれていない一般的な観点（命名・可読性・重複排除・関数の長さ等）も当然に適用する。**
書いていないのは知られているからであって、見なくてよいからではない。

## 共通観点

- CI が全パスしている
- PR 本文に `Closes #{issue番号}`（シリーズ途中は `Refs #`）がある
- コミットメッセージが接頭辞規約（`feat:` / `fix:` / `docs:` 等）に従っている
- ディレクトリ境界違反がない
- 不要なファイル（`.env` / `node_modules` / ビルド生成物 / 一時ファイル）が含まれていない
- 秘匿情報（API キー・トークン・パスワード）が含まれていない
- コメントは日本語で、**意図（何をするか・何を崩すと壊れるか）だけ**を書いている。経緯・Issue 番号・日付・以前の形は書かない（`git log` / PR が持つ）
- **既存の記述と重複する追記、経緯の追記は指摘する**（「明記せよ」と同じ重さで「減らせ」も指摘する）
- 機能追加・変更に対応するドキュメント更新が同時に入っている

## 根拠の取り方

- **根拠のない指摘は書かない。** 根拠は、該当ルールの引用元・実測結果・公式ドキュメントの URL のいずれか。
  **根拠は 1 つで足りる。長さは検証の質の代わりにならない**
- **存在しない機能・ファイル・オプションへの言及**を指摘するときは、実在しないことを自分で確かめてから書く
  （読めるはずのファイルは読む。読めない領域なら「実在しないと断定しない」）
- **推測で判定しない。** 確かめられなかったことは「未確認」と明示する

## 判定基準

- **APPROVE**: 修正必須の指摘 0 件、かつ CI 全パス
- **REQUEST_CHANGES**: 修正必須の指摘が 1 件以上、または CI 失敗
- 好みの問題・将来課題は修正必須に数えない（指摘には残し、根拠に「任意」と明記する）
- 任意と判定した指摘は**レビューコメントに書いて終わり**にし、Issue に起票しない。
  ⚠ **修正必須と判定した指摘の扱いは変わらない**——本 PR 内で解消させる（Issue 送りで PR を通すことはできない）
- 指摘が「既存の齟齬（本 PR に起因しない）」である場合は、次の 2 点を行う
  1. 指摘自体はレビューコメントに残す（本 PR 起因でない旨と、そう判断した根拠を明記する）
  2. 修正必須には数えない（APPROVE / REQUEST_CHANGES の判定に影響させない）

## レビュー結果の定型フォーマット（省略・改変禁止）

機械での判定読み取りと集計を可能にするため、見出し・ラベルを**そのまま**使う。

```
## レビュー(reviewer)
判定: APPROVE / REQUEST_CHANGES
観点: [事実検証 / SSOT 整合 / 設計一貫性 / テスト妥当性 / セキュリティ]
指摘:
1. <ファイル:行> 内容 — 根拠
未解決:
```

記入ルール:

- **`## レビュー(reviewer)` の見出しを必ず含める**（この見出しが無い投稿は判定として読まれない）
  - ⚠ **括弧の中身の揺れ**（`## レビュー(claude)` 等）**はスクリプト側が吸収する（仕様）**。
    機械が見るのは「コードブロックの外にある行頭 `## レビュー`」で、行頭でない形（`> ## レビュー`）と
    コードブロックの中は見出しとして読まれない。**書く側はこの定型のまま書く**
- **`判定:` 行は行頭固定・表記ゆれ禁止**
  - 行頭は必ず `判定: ` で始める。**先頭に空白・引用符（`>`）・リスト記号（`-` `*`）・番号を置かない**
  - **装飾を付けない**（`**判定: APPROVE**` は不可）
  - **コードブロック（\`\`\` や `~~~` で囲った中）に入れない**
  - 値は `APPROVE` または `REQUEST_CHANGES` のいずれか一方**のみ**。大文字・半角で書き、和訳・省略・併記をしない
  - コロンは**半角 `:` + 半角スペース 1 個**（全角 `：` は不可）
  - 1 コメントにつき `判定:` 行は 1 本だけ。過去の判定を引用・再掲しない
- `観点:` は実際に適用した観点だけを角括弧内に列挙する（適用外は消す）
- `指摘:` は `<ファイル:行>` から始め、末尾に `— 根拠` を付ける。指摘なしの場合は `なし`
  - **1 件 2 行以内**: `<ファイル:行> 何が問題か — 根拠（1 つ）`。根拠は引用元・実測値・URL のいずれか 1 つとし、複数を並べない
- `未解決:` は人間の判断が必要な事項。なければ `なし`
  - 「本 PR に該当しない観点」「CI に委ねる」のような確認記録は書かない
- **APPROVE のときは `指摘:` `未解決:` ともに `なし` だけを書く**。確認した内容・突き合わせた結果の列挙は書かない（確認したことは判定に織り込まれている）
- **実測の生ログ**（`harness.md`「破壊的スクリプト」「ガード判定ロジックの変更」）を載せるときは、本文には結論 1 行だけを書き、ログは同じコメント内の `<details>` に畳む。
  ⚠ **`<details>` の中に `判定:` 行・`## レビュー` 見出しを入れない**（`<details>` はコードブロックではないため機械に読まれる）

**このフォーマットは Approve スクリプト（`scripts/approve-if-verdict.sh`）の契約である。**
機械が読むのは**コードブロックの外にある行頭 `## レビュー` の見出し**（括弧の中身は見ない）と、
**同じくコードブロックの外にある行頭 `判定:` 行がちょうど 1 本**あることの 2 つで、
どちらかの形を外すと判定が読まれず Approve が付かなくなる。

## 投稿の作法

本文は `mktemp -d` が返した一時ディレクトリ配下にファイルとして作り、その本文ファイルの絶対パスを `--body-file` に渡す。

```bash
gh pr comment <PR番号> --body-file <一時ディレクトリ配下に作った本文ファイルの絶対パス>
```

- 本文を 1 行に圧縮しない（判定行が行頭に来なくなり、判定として読まれない）
- 投稿は **1 PR につき 1 件**にまとめる
- inline コメント（review thread）は使わない（未解決スレッドとしてマージを止めるため）

## Approve の押し方（Claude 自身は `gh pr review` を使わない）

判定は `gh pr comment` + 行頭の `判定:` 行で投稿する。**Claude 自身は `gh pr review --approve` /
`--request-changes` を実行しない。**

- **GitHub Actions 上での実行**: 正式な Approve は Claude ではなく後続ステップの
  `scripts/approve-if-verdict.sh` が押す（`github-actions[bot]` の投稿から判定行を機械で読み、
  `判定: APPROVE` のときだけ `GITHUB_TOKEN` で Approve する。`REQUEST_CHANGES` なら何も押さない）。
  `gh api` / `gh pr review` / inline コメント MCP は許可されていない
- **ローカルでの実行**: PR 作成者とレビュー実行者が同一の GitHub アカウントの場合、
  `gh pr review --approve` は GitHub の仕様（"Pull request authors cannot approve their own pull requests."
  [GitHub Docs](https://docs.github.com/en/pull-requests/collaborating-with-pull-requests/reviewing-changes-in-pull-requests/reviewing-proposed-changes-in-a-pull-request)）
  により通らない。**試行しない**。**この場合の判定行は Approve には数えられない**
  （`approve-if-verdict.sh` は `github-actions[bot]` の投稿しか読まない）
- Approve の有無は UI の「Reviewers」欄ではなく
  `gh api repos/<owner>/<repo>/pulls/<PR番号>/reviews --paginate --jq '.[].state'` で測る
  （`--paginate` を省くと既定の 1 ページ分で切れる）

## 禁止事項

- レビュー中に成果物を修正すること（修正は作成者が行う）
- PR のマージ・クローズ（マージ判断はレビュアーの仕事ではない）
- 根拠のない指摘・推測に基づく判定
- 指摘のためだけの指摘（件数を稼ぐための軽微な言い換え要求）
