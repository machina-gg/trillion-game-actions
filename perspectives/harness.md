# harness プロファイル

エージェントの**運営ルール文書・CI 定義・自動化スクリプト**を持つリポジトリ向けの観点。
`common.md` に足して適用する。

対象は次の 2 群で、**`.github/workflows/` は A と B の両方に該当する**（A = 事実検証・SSOT 整合 /
B = ロジックとガードの検証）。両方を適用する。

## A. ルール文書と CI 定義（`CLAUDE.md` ・ エージェント設定ディレクトリ ・ `.github/workflows/`）

### 事実検証（最重要）

AI が生成した文書・CI 定義は、事実の裏取りが最も甘くなる。

- 公式ドキュメント・チェンジログの引用に URL があり、その URL を実際に開いて記述と一致するか（`WebFetch` で確認する）
- **存在しない機能・ツール・オプションへの言及**がないか。workflow では **`uses:` の action とそのバージョン・
  `run:` が呼ぶスクリプトのパス・参照する `secrets` / 環境変数名**が対象。
  ⚠ **確認手段は対象ごとに違う**
  - スクリプトのパスと `env:` で定義した環境変数 → ファイルを読んで、定義と参照を同一ファイル内で突き合わせる
  - action とそのバージョン → `WebFetch`（ファイルを読むだけでは届かない）
  - `secrets` 名・Actions variables → **リポジトリ設定側にあり、読めないことがある**。
    他の workflow での使用実績と名前の一致だけを見る（**実在しないと断定しない**）
- 参照されているファイルパス・スキル名・エージェント名が実在するか（ファイル一覧で確認する）
- **文書に書かれたコマンドを検証するときは、手で書き写さずファイルから逐語抽出して実行する**
  （書き写すと転記ずれで「検証したつもり」になる）
- **base の鮮度確認（false-positive 対策）**: PR ブランチの分岐点が古いと、
  「存在するはずのファイルが無い」等の false-positive が起きる。
  ファイル不在を指摘する前に、base とブランチの比較（`compare` 相当）で分岐点の鮮度を確かめる。
  ⚠ チェックアウトした `HEAD` の位置に依存する確認方法を使わない（レビュー実行環境では `HEAD` が
  base のままのことがあり、分岐点を正しく検出できない）
- 実測値・件数（「N 体」「N 件」等）が実際の数と一致するか
- **未承認の設計判断が紛れ込んでいないか**（Issue に書かれていない仕様・ルールを独自に追加していないか。
  Issue 本文と差分を突き合わせる）

### SSOT 整合

- 同じ内容が複数箇所に重複記載されていないか（実体 1 箇所 + リンク参照になっているか）
- 既存の記述と矛盾していないか（変更したルールの旧記述が他ファイルに残っていないか。全文検索で残存を確認する）
- **腐るもの**（日付・実測値・件数）を書いていないか。必要なら「測り方」が書かれているか
- 分類が適切か（手順・観点と、参照用の知識が混ざっていないか）。⚠ **本項は `.github/workflows/` には適用しない**
- 用語・呼称の規約に違反していないか（規約はリポジトリの `CLAUDE.md` が持つ）

## B. スクリプト・hooks・`.github/workflows/`

- **同一ファイル内の全ガードの再検証**: 変更したガードだけでなく、**同じファイル内の全ガードを
  主要な自動実行経路の実 diff に通す**
- ⚠ **隣のガードとの衝突は本 PR の CI では検出できないことがある**（その workflow がブランチ条件で
  スキップされ、自分が壊したガードを自分の CI が一度も実行しない形があり得る。
  **CI が緑のまま、次に走る実行を必ず落とす状態が残り得る**）
- **回帰テストの妥当性**: 変更したロジックに対応するテストが追加され、変更前のコードでは落ちるテストになっているか
- **fail-open / fail-close の判断**: エラー時・想定外入力時にどちらへ倒れるか。その選択が明記され、
  対象の性質（安全性が要るなら fail-close、開発を止めない性質なら fail-open）と整合しているか
- hook / job のタイムアウト・終了コードの扱いが仕様どおりか
- 標準出力・標準エラーへの出力が hook / workflow の契約を壊していないか
- 秘匿情報（トークン・パス以上の環境情報）をログ出力していないか
- 外部から与えられる値（workflow の `inputs` / PR タイトル・本文・ブランチ名）を、検証せずに
  シェル・プロンプト・ログ出力へ素通ししていないか

### 破壊的スクリプト

ファイルの削除・移動・上書き、または git 履歴を変更するスクリプトを追加・変更する PR では、次の 2 点を見る。

- **独立実行**: 実装者の報告を根拠にせず、**自分でスクリプトを実行して挙動を確認する**。
  検証用の一時リポジトリ等を作り、保護されるべきケースと削除されてよいケースの両方を実測する。
  実測した生のコマンドと出力は貼る（本文への畳み方は `common.md`「レビュー結果の定型フォーマット」記入ルールに従う）
- **失敗方向の確認**: エラー・例外時にどちらへ倒れるかを確認する。破壊的操作のガードは、
  判定できないときに**実行しない側**（fail-close）へ倒れる必要がある

### ガード判定ロジックの変更

危険操作を止める判定ロジックを変更する PR では、**テストが全て通っていても fail-close 回帰
（deny が pass に緩む退行）を含み得る**（テストの green は「回帰なし」を意味しない）。上記に加えて次を実測する。

- **base / head 突き合わせ**: 同一の実入力コーパスを base と head の両方の判定ロジックに与えて差分を取り、
  **pass→deny（安全側）以外の変化**（deny→pass / ask→pass / deny→ask）を全件検出して 1 件ずつ理由を特定する
- **素通り方向の探索**: 入力に、入れ子の実行文脈（コマンド置換・バッククォート・プロセス置換）・
  セグメント境界の細工・境界値（上限 ±1）を必ず含める
- **変異テストの確認**: 検出・除外ロジックを無効化した変異でテストが落ちること、および
  head のテストを base 実装に当てると落ちることを確認する

⚠ **GitHub Actions 上のレビューではスクリプトを実行できない**（実行系のツールを許可していない）。
この 2 節に当たる PR では、**実行できるレビュアーによる別のレビューが必要**であり、
GitHub Actions 上のレビューだけで済ませてはいけない。その旨を `未解決:` に書く。
